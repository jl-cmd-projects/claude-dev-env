# The review loop runs before the merge

A pull request the agent made merges once a pass is clean. After three full passes with fixes, a later pass files its remaining findings in one issue, and the pull request merges. Loop it:

1. Review the head with the command `CLAUDE_MERGE_REVIEW_COMMAND` names. Where it is unset, run `/code-review high --max-findings all` against the base. This is a full pass.
2. Record the pass: `python3 ~/.claude/scripts/merge_review_receipt.py <owner>/<name> <number> <head sha> <finding count>`. The receipt counts the pass. Each new head is the next pass, and recording the same head again keeps its pass. A record with `--filed` also reads GitHub: its pass is never lower than one more than the earlier pull request commits whose review run failed for this pull request, so a new session keeps the count.
3. Fix every valid finding, push, and review the new head. Answer each finding you rule out on the pull request with its file:line evidence.
4. Passes 1, 2 and 3 are full passes, and each finding they report is fixed in this pull request. After the third pass's fixes, review the new head with `/code-review low <number>`. It reads only the pull request's diff against its base. Name the number: after a push, a bare `/code-review low` diffs the branch against its own upstream and sees nothing.
5. A pass that records `CLEAN` ends the loop. A pass whose every finding is ruled out records `CLEAN` with `--ruled-out <finding count> --rulings <link to the rulings comment on this pull request>`.
6. When pass 4 or a later pass still reports findings, do not loop again. File one issue in the same repository that lists them, push no fix for them in this pull request, and record the pass again with `--filed <issue url>`. It prints `FILED`. Findings you rule out on that pass add `--ruled-out` and `--rulings` as in step 5 and stay out of the issue. Before pass 4, `--filed` is refused. The receipt script reads the issue with `gh` and refuses a link that names no issue in that repository.
7. A security finding is the exception. Fix it in this pull request or rule it out with evidence, in any pass, and never file it. A fix pushes a new head, which gets its own pass.
8. Merge pinned to the head of the `CLEAN` or `FILED` pass: `expectedHeadSha` on the merge tool, or `--match-head-commit` on `gh pr merge`.

One review pass runs before the pull request opens. Run `/code-review high` on the branch diff, with `/security-review` where it is installed, or have a fresh-context subagent review it. Record that pass from the checkout of the branch you will open, with `open` in place of the number and the full 40 character head it saw: `python3 ~/.claude/scripts/merge_review_receipt.py <owner>/<name> open <head sha> <finding count>`. Fix each valid finding in a new commit on top of that head, push the fix commits with `git push origin HEAD:refs/heads/<branch>`, then open the pull request. The fix commits need no second pass, and the gate allows the open at any head that sits on them. A pass with zero findings opens at the reviewed head itself. So does a pass whose every finding is ruled out with `--ruled-out <finding count> --rulings <path:line for each finding, comma separated>`; run it in the checkout that holds the head, which checks that each `path:line` exists there, and give each finding a different one. A reviewed commit that another branch holds without the head, such as a commit of `main` or of the branch a stacked branch builds on, does not cover the open. The head branch's own `origin/<branch>` reference, left at the reviewed commit before the fix commits, is the same branch and does not withhold credit. Nor does a pass recorded on another branch, which the receipt names. A pass recorded while another branch held the reviewed head, outside the branch's checkout, or on a detached `HEAD` names no branch, so it counts only at that head; the script says so, and the deny reason says to record the same pass again from the checkout of the branch. The gate reads the head the pull request opens with from GitHub, for a shell create too, so push the fix commits before the open. It reads that head before the command runs, so push in one command and run the create on its own in the next. A clean head gives credit only when, before the create, the command holds nothing but `cd` or `pushd` with one plain folder whose path has no part ending in `.git` and a bare `cat`, `echo`, `printf`, `head` or `tail` that writes no file; title and body substitutions run only `cat`, `echo` or `printf`, with a quoted heredoc delimiter when the body holds `$`; the command holds no `<(` or `>(`, and, outside single quotes, no `$[`, no `$((` and no braced expansion but a plain `${name}` or a `${name:-word}`, `${name:+word}` or `${name:?word}` default; and the create's output goes only to `/dev/null`, a plain file outside `.git` or a pipe into `cat`, `head`, `tail`, `tee` or `grep`. Any other shape is denied at a clean head. A reviewed commit that the base branch holds on GitHub does not cover the open, and the open is denied when that base cannot be read. With no `--base`, the base is the head branch's `gh-merge-base` setting, then the default branch, as gh reads it. A create tool call with no `base`, or a shell create that is not the whole command, gets no credit for an earlier pass; run `gh pr create` alone, or the `pull_request.py create` launcher alone as `~/.agents/skills/pull-request/scripts/pull_request.py`, written with `~/`, `$HOME/` or the full home folder, with `--repo`, `--base` and `--head` each given once with a value, and keep its other words to text that holds none of `(`, `)`, `;`, `<`, `>`, `|`, `&`, `#`, `{`, `}`, `*`, `?`, `[`, `~` outside quotes, and no `$`, a backtick or a line break anywhere. Another script named `pull_request.py` gets no credit. A quoted title such as `"Fix edge cases (Windows)"` keeps the create alone. A create with no `--head`, or with an empty `--head` such as `--head=`, gets no credit from any pass when the branch's git settings may send gh to another branch name or remote, such as a `branch.<branch>.merge` that names another branch; name the head with `--head <branch>`. A create word that bash can expand into words the gate does not read is denied at any head: a `$`, backtick, brace, glob or leading tilde outside quotes, a `"$@"`, or a `$` or backtick inside double quotes in a flag or its value. A word is a title, body or label value only when gh reads it as one, so `--title -t "$X"` is denied. Title and body text may hold `$(...)` and glob characters inside quotes. Write each flag as a plain word, and quote title and body text or pass `--body-file`. An open pass does not take `--filed` and does not count toward the three full passes above. A merge pinned to the reviewed head passes on an open pass only at zero findings. Rulings for the merge go on the pull request, as in step 5.

`hooks/blocking/merge_review_gate.py` denies any other merge. In a merge-queue repository, enqueue with `gh pr merge <number> --repo <owner>/<name> --auto --match-head-commit <head sha>`; auto-merge that names no head is denied. A repository whose own CI and merge queue review and merge its pull requests is listed in `CLAUDE_MERGE_REVIEW_EXEMPT_REPOSITORIES`, comma separated as `owner/name`, and skips the gate.
