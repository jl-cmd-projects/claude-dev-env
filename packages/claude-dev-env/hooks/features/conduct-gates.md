# Conduct gates

This family stops a chat reply, edited message, or tool call when its payload breaks a session rule. Each gate gives the agent a reason it can act on.

## Checks

- `blocking/final_reply_gate.py` checks the reply a session ends its turn with. Its `windows_path_violation` blocks a path the terminal would render without one of its backslashes. Its `unbriefed_question_violation` blocks a reply whose last paragraph, with fences, quotes, and code spans left out, ends with a question mark or says a question still stands, when the turn sent no `AskUserQuestion`, hearthbot decision card, or Codex `request_user_input` call; it is skipped when the transcript cannot be read.
- `blocking/open_tasks_stop_gate.py` holds the end of a turn once when the prompt that started it asks for work, the turn ran a work tool, and the turn made no tracker call: TaskCreate, TaskUpdate, TodoWrite, the Codex `update_plan`, or the desktop `mcp__ccd_turn__update_plan`. A work tool is any tool but a tracker call, the session title tool, `AskUserQuestion`, a hearthbot decision card, Codex `request_user_input`, `ToolSearch`, `TaskList`, or `TaskGet`. It also holds the turn once when completed items sit beside open ones on the task list the user sees: the session's task store, or the transcript's list when the session has no store. A list that `CLAUDE_CODE_TASK_LIST_ID` shares with other sessions is left alone. It also holds the turn once when the closing reply, or a Markdown, text, or HTML file the turn sent with `SendUserFile`, says something waits on the user and the turn ran no read call or sent no question tool call. `blocking/user_step_wording.py` finds that wording: phrases such as "needs you", "waiting on you", "you need to", and "say when", outside fences, quotes, and code spans, unless a negation on the same line covers the phrase ("Nothing here needs you", "This change does not need you") or the phrase is a label with nothing under it ("Action required: none."). The module docstring of `blocking/user_step_wording.py` names each skip shape. Every other wording is held, because a wrong hold costs the agent one step and a wrong skip hides a step from the user. "Say when" counts only at the start of its clause. Markdown and plain text are read one paragraph at a time. In an HTML file it reads the text one block at a time, counts white space in the source as one space and a `br` as a line break, and leaves out the contents of `script`, `style`, `template`, `title`, `textarea`, `noscript`, `code`, `pre`, and `blockquote` elements; text under a hidden attribute still counts. It skips a sent path that is no regular file and a file over 256 KB, and reads a path sent twice once. A read call is a shell, a file or web read, a subagent, a Codex `local_shell_call`, or a tool whose name carries a read word such as `get`, `list`, or `read` and no write word such as `update` or `append`. Only the part of an MCP tool name after the server is read, and it is split into words at underscores, hyphens, and a capital that follows a lower-case letter or a digit. `TaskList`, `TaskGet`, `ToolSearch`, and the question tools do not count. The gate checks that a read ran and leaves which item it read to the agent, so each such hold tells the agent to read the live state of every item it shows as open, and to end the turn when the wording hands the user no step. One reason carries every finding. `open_task_asks.is_ask` decides whether a prompt asks for work: a question-only prompt, an acknowledgement such as `thanks!`, an empty prompt, a prompt of only `<system-reminder>` blocks, and an envelope such as `<agent-message>` or `<task-notification>` do not. `blocking/open_tasks_transcript.py` replays the transcript for it: the turn's prompt, its tool calls, and the task list. `session_task_items` merges the task store with the transcript items whose subject the store does not hold.
- `session/tracking_nudge.py` adds one `additionalContext` note to a prompt that asks for work. The note asks for an item in the session's task list tool. It shows on the session's first ask and on the first ask after each compaction, through `once_per_session.py`. When the title shows the red flag or the check mark, it also asks for the hourglass before other work. In a session that has a `__set_session_title` tool and no title yet, it asks once for a first title in the `⏳ <name>` form, and never again in that session, compactions included, through `once_per_session.claim_only_showing`. On a turn that an event starts, with no message from the user, it adds one wake note while the title shows the red flag. The note names that title and asks for the status that fits now if the event cleared what the user had to do. It shows on each such prompt and on no other title. The hook runs only when a prompt starts a turn, so a notification that reaches the agent in the middle of a turn gets no note. `tracking_nudge.is_event_wake` counts a prompt as an event only when it opens with one `<task-notification>` envelope with a bare opening tag, or one `<agent-message>` whose opening tag has `from` as its only attribute, both in lower case, with nothing after it but `<system-reminder>` blocks. A sender that is empty or `human`, in any letter case and with white space around it ignored, is no event. The first closing tag ends the envelope, so a body that quotes its own closing tag reads as typed text after the envelope and gets no wake note. A `<wake reason="external-event">` envelope, a plain `[SYSTEM NOTIFICATION - NOT USER INPUT]` prompt, two envelopes in one prompt, an envelope with a lead line before it, and an opening tag with another attribute or letter case get no wake note. Of these, a prompt with a lead line, a plain system notification prompt, and a tag in another letter case can still get the ask notes when they ask for work. `session_title_transcript.py` reads the title tool and the shown title from the transcript. It never blocks. No hook holds the end of a turn for the title.
- `session/background_silence_prompt.py` adds one `additionalContext` note to a background event prompt, one that starts with `<task-notification>` or opens itself or a `<system-reminder>` block with `[SYSTEM NOTIFICATION - NOT USER INPUT]`, while the user asked for silence. The newest user-typed message that sets silence ("silent unless", "stay silent", "silent on updates", "no updates unless") or lifts it ("you can talk again", "updates are fine", "stop being silent") decides. The note quotes the user's "unless" or "except" clause word for word, or the whole message when it has no such clause, and says to end the turn with no text unless that exception applies now. Envelope prompts, compaction summaries, and quoted `>` lines are not the user's words. It never blocks.
- The claim judge is a `prompt` hook in `hooks.json`, with no `model` set, so Claude Code's small default hook model reads each chat message and denies every claim, numbered in one refusal, about how code, a file, a tool, a service, a run, or a process behaves, or why something happened, when nothing in the message shows it: inline code that quotes output or a code line, a file and line, or a link. A pull request link covers what that change does, what it blocks or lets through, and its checks. The author's own actions, a restatement of the user's words, questions, instructions, and a decision card's option consequences pass. It catches plain claims such as "The code lets any of them rewrite it mid-check." `continueOnBlock` returns the reason to the agent as the tool error, so it can add the source and send again. The installer owns it through the `claude-dev-env: ` prefix on its `statusMessage`. It skips `post_widget`, whose input is SVG or HTML markup.
- `blocking/edit_marker_gate.py` rejects strikethrough and edit-note markers in replacement chat text or cards.
- `blocking/issue_close_handoff_gate.py` denies an issue comment or issue write that closes the issue and routes a found defect to another issue or epic.
- `blocking/session_title_format_gate.py` denies a session title that breaks the `<emoji> <name>` shape or has a name longer than 25 characters.
- `blocking/task_subject_outcome_gate.py` denies a TaskCreate or TaskUpdate subject, or a TodoWrite item, that starts with a procedure step label (step, phase, stage, part, feature, bug fix, refactoring, or playbook, then a one- or two-digit number or range, then `:`, `)`, or a `.` that no digit follows) or holds a backtick. The reason says to name the item by its outcome in the user's words and keep procedure steps in a private checklist file. A status-only TaskUpdate passes.
- `blocking/task_subject_length_gate.py` denies a `TaskCreate` or `TaskUpdate` whose `subject` is over 80 characters, and a `TodoWrite` whose list holds an item `content` over 80 characters, naming the first such item. The reason gives the length and the limit and says to start with who acts (Me, You, or Handed off), say what is left, and put detail in the description.
- `blocking/step_note_gate.py` requires a status line before a tool call while its opt-in flag is on.
- `blocking/wakeup_cap_gate.py` keeps a self-wakeup inside the 1-hour prompt cache. A wake over the step-down (57 minutes for `send_later` and Routines, 3480 seconds for `ScheduleWakeup`) and at most 60 minutes away runs with its delay rewritten to the step-down. A wake over 60 minutes away, or a cron with more than 57 minutes between wakes, is denied with a reason that says to stack wakes under the cap. A Routine that starts a fresh session on each firing passes.
- `blocking/verify_before_acting.py` blocks a completed mutating call when the agent's reasoning contains an unchecked claim. For an `Agent` or `Task` spawn it adds the same quote as an advisory note and does not block.
- `blocking/pr_lifecycle_skill_gate.py` denies a commit, push, pull request action, or merge until the `pr-lifecycle` skill appears in the transcript since the last compaction. The scan reads the transcript newest line first, so the first load or compaction boundary it meets decides. Every create spelling the shared listing in `blocking/followup_pr_dedupe.py` reads counts as a pull request action. Read-only `gh pr` subcommands (`view`, `list`, `checks`, `diff`, `status`) pass without it, unless a later argument names another `gh pr` subcommand.
- `blocking/resolve_thread_reply_gate.py` denies a review thread resolve until the agent's own transcript shows a reply on that same thread that posted after the last user prompt and that no successful resolve of the thread has spent. A resolve is a `resolve_review_thread` call, which names the thread by `threadID`; a `pull_request_review_write` call with method `resolve_thread`, which names it by `threadId`; a shell command with a `gh api graphql` `resolveReviewThread` mutation, which names it by a literal `PRRT_` id; or a shell call to `pulls/<n>/ccr/comments/<id>/resolve`, which names it by a comment id. A graphql resolve that names no `PRRT_` id is denied. A reply is an `add_reply_to_pull_request_comment` call, or a `gh api` call to a comment's `replies` endpoint or to `addPullRequestReviewThreadReply`, which names its thread by `PRRT_` id. A shell command that is one plain `review_reply_post.py request` call is a reply on the comment its `--comment-id` names and on the thread its `--thread-id` names. The launcher is absent, or is `python`, `python3`, `python3.<n>` or `py`, with or without `.exe`, bare or by an absolute path that starts with `/` or with a drive letter and `:/`. The script's parser accepts any prefix of an option name, so each word after `request` must be `--pull`, `--comment-id`, `--thread-id`, `--body-file` or `--wait-seconds` with a value that starts with no `-`, or the bare `--supersede`, each given once. A command that holds `;`, `&`, `|`, a redirect, a subshell, a substitution, a variable, `#`, a brace, a glob, `~`, `!`, a backslash or a line break is no reply. So a `cd dir &&` prefix, an environment prefix, a launcher option such as `python3 -u` or `py -3`, a launcher by a relative path such as `.venv/bin/python`, `uv run`, a line continuation, a backslash path, a pipe to `tail`, and a quoted value that holds `(`, `[` or `~` all count for nothing; run the plain form. A file of the same name, or a launcher of the same name at an absolute path, that exits 0 without posting still counts. A reply and a resolve by comment id match when they name the same comment, or when a successful tool result in the transcript, such as `pull_request_read` `get_review_comments`, lists the comment under the thread by its `discussion_r` anchor or `databaseId`. A reply whose result is an error does not count. A background task notice is no user prompt, so a reply before it still counts. A call runs in the background when its `run_in_background` input is truthy, or when it is a `Bash` or `PowerShell` call whose result holds a line that starts `Command running in background with ID:`, `Command was manually backgrounded by user with ID:` or `Command did not complete within`. Those words in the result of any other tool, such as a reply tool that returns the comment body, change nothing. Such a reply counts only once a notice names its tool use id and a completed status before its summary, and ends its summary with `completed (exit code 0)`. The notice is read from a user entry or from a `queued_command` attachment, and a text that holds two notices vouches for no call. Any other `queued_command` attachment, such as a prompt the user sent mid-turn or a message another agent queued, ends the turn as a user prompt does, so a reply before it does not count and the agent replies again before it resolves. With no readable transcript, the resolve passes.
- `blocking/verify_before_commit_gate.py` denies a `git commit` in a repository with a `.claude/skills/verify` or `.agents/skills/verify` directory until the `verify` skill loads after the last user prompt, through a Skill call whose result comes back without an error, or the `/verify` command in that prompt. It reads the committed paths from the staged diff, the tracked changes for `-a`, and the paths of each `git add` earlier in the same command, and passes a commit whose paths are all docs, images, test files, or `.json`, `.jsonl`, `.yaml`, `.yml`, or `.csv` files under a `docs` folder.
- `blocking/build_eval_before_eval_write_gate.py` denies a write to an eval file until a Skill call named exactly `claude-api` with args `build-eval`, or the `/claude-api build-eval` command, appears in the transcript.
- `blocking/merge_review_gate.py` denies an agent's merge until a review pass on the merged head reported zero findings, or ruled out every finding and linked the posted rulings. It reads the receipt `scripts/merge_review_receipt.py` writes, requires the merge, auto-merge or merge-queue entry to be pinned to that head, and skips repositories listed in `CLAUDE_MERGE_REVIEW_EXEMPT_REPOSITORIES`. A `gh pr merge` call whose every merge segment carries `--disable-auto` only turns auto-merge off, so it passes. A segment that also carries `--auto`, gives `--auto` or `--disable-auto` an `=` value, joins short flags such as `-sb`, or holds a bare `--` keeps every check. Its deny reason names the review command `CLAUDE_MERGE_REVIEW_COMMAND` sets. The reason tells the agent to run that command for the first three passes and `/code-review low --fix <number>` for each later pass; the gate itself counts no passes. It also denies a pull request open, through a shell create or a `create_pull_request` tool, until a pass recorded as `merge_review_receipt.py <owner/name> open <head> 0` covers the head the pull request opens with. A shell create is any spelling the shared listing in `blocking/followup_pr_dedupe.py` reads: `gh pr create`, `gh pr new`, `gh` with a root `-R` or `--repo` before `pr`, a `GH_REPO=` prefix, and `pull_request.py create` run by any `python`, `python3.x`, `py` or `uv run` launcher, with interpreter options or a path to the script. A command that chains several creates is checked create by create, in command order, and the deny names the first head with no clean pass. Each create reads its repository as gh does: among every `-R`, `--repo`, `--repo=`, `-R=` or clustered `-dR` flag before or after `pr`, the last one decides, and a flag word that is the value of another option, such as `--title --repo=x/y`, is not a flag. `blocking/merge_review_gate_parts/create_options.py` reads each value as gh does: an option that takes a value takes the next word, so `--title -Hx` and `--body -H --title x` name no head, and in a short cluster such as `-bHx` the first letter that takes a value takes the rest of the cluster. With no flag it reads the last `GH_REPO=` prefix, then the origin remote. A wrapper such as `env -u GH_REPO`, `env -i` or `sudo` can drop the prefix before gh runs, as in `GH_REPO=o/r env -u GH_REPO gh pr create`, where gh opens in the origin repository. So every create the walk reaches whose repository comes only from a `GH_REPO=` prefix needs a clean pass for the prefix repository and for origin, also when the prefix value names no repository, and its deny for origin says to name the repository with `--repo owner/name` on the create. The walk steps over `env`, `sudo` and `timeout` with their options, and over the launchers `nohup`, `nice`, `stdbuf`, `setsid` and `time` when each launcher option holds its value in the same word or takes a number, as in `stdbuf -o0` or `nice -n 5`. It also reads a create behind `command` or `exec`, as in `command env -u GH_REPO` or `exec nohup env -u GH_REPO`. A create after the first one is not read behind a program the walk does not step over, such as `ionice`, `flock` or `doas`, or behind a launcher option with a separate value that is not a number, such as `stdbuf -o L` or `time -o out.txt`. A create that passes `--repo owner/name` needs a pass for that repository only. Two creates with the same options stay two checks when one has a prefix and the other does not. The first create in a command is also read the way the gate read it before it walked every create: its repository comes from a `--repo` flag or the origin remote, never from a prefix. A `GH_REPO+=` append, in a create's own prefix or anywhere else in the command, counts as a set whose value the gate cannot read. When the command sets `GH_REPO` anywhere outside a create's own prefix, through an assignment before another program, such as `GH_REPO=o/r bash -c ...`, or through an `export`, `declare`, `typeset`, `local` or `readonly` word that names `GH_REPO`, each create that names no repository flag and no `GH_REPO=` prefix of its own is denied as unread, and the reason says to pass `--repo owner/name`. The gate does not follow where that value reaches. `blocking/followup_pr_dedupe.py` reads the same condition through the same `sets_gh_repository` helper and refuses such a follow-up create, with a reason that says to name the repository with `--repo`. For a follow-up create whose repository comes only from a `GH_REPO=` prefix, it reads the open pull requests of the prefix repository and of the origin remote, since a wrapper can drop the prefix; a prefix value that names no repository, such as `GH_REPO=nonsense`, still gets the origin read, and a deny from the origin read opens with the sentence to name the repository with `--repo owner/name`; when the origin remote names no GitHub repository it reads the prefix repository only. A duplicate found in origin that way is refused with a reason that says to name the repository with `--repo owner/name` on the create, and a create that names its repository with its own `--repo` reads that repository only. Each head it names through `-H x`, `-Hx`, `-H=x`, `--head x`, `--head=x` or a cluster of short flags such as `-dHx`, `-dH x` or `-fH=x` gets its own check, also a head a later head flag overrides, as gh reads each one. A create that names no head reads `HEAD`. The first-create reading takes a head only from `-H x`, `--head x` or their `=` forms, so a create that gives its head as `-Hx` is also checked on `HEAD`; name the head with `--head` when the working folder is on another branch. `blocking/merge_review_gate_parts/create_folders.py` walks the command to give each create its folder, and `blocking/merge_review_gate_parts/folder_state.py` holds that folder, whether it is followed, and the `pushd` stack. The walk follows `cd`, `chdir`, `Set-Location`, `pushd` and `popd`, also after `builtin` or `command`; the end of a subshell, back to the folder in effect when that subshell opened, also when nested subshells close together on one line or across line breaks; and `eval`, which changes the folder of its own shell. A create inside `bash -c`, `sh -c` or a command substitution runs in the folder before it, also when a line break inside the script comes before it. A `cd` in a background job stays in that job. The walk does not model a folder change in a pipeline member, a brace group, `if`, `case`, `for`, `while`, `until`, `select` or a function body, a folder change after a redirect, or a folder word anywhere but the program place. Each later create in that scope is denied as unreadable. So is each create after a folder the walk cannot name, such as `cd "$VAR"`, `cd -` or a glob, and each create after a folder change the walk cannot follow, such as `popd` with nothing pushed, in any wrapper. A create in a folder that does not exist gets no git answer and is denied as unreadable. Text nested past 16 levels of `bash -c`, `eval` or substitution that names `gh` and a `create` or `new` word, or names `pull_request.py`, gives one create whose folder is not followed, so it is denied as unread. `blocking/merge_review_gate_parts/quoted_lines.py` cuts the text into lines and words as bash reads its quotes: `\"` inside a double-quoted value does not end the value, an ANSI-C `$'...'` value is one word, and a line break ends a command only outside quotes, subshells and substitutions. So the walk reads no command in a heredoc body or in a quoted option value, such as `--body "a; gh pr create --head x"`, with or without a line break inside it. It does read the script that `bash -c`, `sh -c`, `pwsh -Command`, `eval` or `Invoke-Expression` gets, line breaks included, and each `$(...)` or backtick substitution, also one inside a double-quoted value, such as `--body "$(gh pr create --head x)"`, since bash runs those. It reads no substitution bash does not run: one inside single quotes, such as `--body '$(gh pr create --head x)'` or `echo '$(gh pr create --head x)'`, or one whose `$(` or backtick a backslash escapes, such as `echo \$(gh pr create --head x)`. It reads `eval`'s words joined by spaces, as bash does, so `eval 'gh pr create --body "a b"'` is one create, and it reads the words after the last `)` inside a segment, such as the command of a `case` arm, as a create and as a wrapper. A command whose quotes do not close is read both ways the earlier walk read it, POSIX and raw words, as written and with its quoted line breaks joined. `blocking/merge_review_gate_parts/wrapped_creates.py` reads each wrapped inner text once more in POSIX words and gives a create the walk did not place as one whose folder is not followed; it skips the command itself, each closed text with its line breaks read as spaces, and each text unwrapped from one, so a heredoc body inside `--body "$(cat <<'B' ...)"` runs no command and `bash -c 'gh pr create\nls'` is one create. The gate also keeps the earlier first-create reading: the first `gh pr create` or `pull_request.py create` the raw text spells outside `--title`, `--body` and `--body-file` values, in the folder of the last `cd`, `pushd`, `Set-Location` or `sl` before it, with its first `--repo` and its first `-H` or `--head` given with a space or `=`. That reading is one more check unless a walk check equals it. So these are checked on the head that first create names: `echo gh pr create --head x | bash`; a create in a heredoc fed to `bash` or `.`; and the first create words after `;`, `&&`, `||` or `|` inside a quoted value, such as a `git commit -m` message. Beyond that first-create reading, the gate does not read: a create a shell gets through its input, a here-string, a heredoc, a process substitution such as `bash <(echo ...)` or a script file; a create in a command string that a program other than `bash`, `sh`, `pwsh`, `powershell`, `cmd /c`, `eval`, `Invoke-Expression`, `find -exec`, `xargs` or `Start-Process` runs, such as `zsh -c`, `su -c`, `ssh`, `watch`, `python -c` or a git alias; or a program name that a variable, alias or function holds. These forms are read in part. A `case` arm inside a double-quoted substitution, such as `--body "$(case x in x) gh pr create ;; esac)"`, is cut at the arm's `)`, so its create is not read. An arithmetic `<<` followed by a word, such as `$((1<<x))`, opens a heredoc for the walk, so the lines after it up to a line `x` are not read; the first-create reading still checks the first create in the raw text. A substitution in an unquoted heredoc body fed to a plain command such as `cat` is not walked; the first-create reading checks the first create there with the closing `)` kept in its head, so that head is unreadable and denied. A create in a heredoc fed to `.` or `bash` is checked only through the first-create reading: it reads `--repo` and a `--head` or `-H` given with a space or `=`, checks a `-Hx` or clustered head as `HEAD`, and does not read a create after the first. The words of a quoted option value are not commands, so a create in one is not read and needs no review. Once the gate knows the call opens or merges a pull request, a check that raises denies the call with the fault reason, which names the error type. A payload read that raises is denied the same way for a `create_pull_request`, `merge_pull_request` or `enable_pr_auto_merge` tool, and for a shell command whose text holds the word `gh` and a `create`, `new` or `merge` word anywhere, or names `pull_request.py`. Any other payload read fault goes to the shared helper. A call that opens and merges nothing gets no such deny. An open pass also counts when every finding is ruled out: `merge_review_receipt.py <owner/name> open <head> <count> --ruled-out <count> --rulings <path:line,...>`, with a different `path:line` for each finding, checked against the file at that head when the pass is recorded. A merge pinned to that same head passes on the open receipt only when the pass found zero findings.
- `blocking/artifact_dark_mode_gate.py` denies an Artifact page publish when the page, inside the publish wrapper, keeps a light body or shows text under 4.5:1 contrast in dark mode. `blocking/artifact_dark_mode_render.cjs` renders the page in headless Chromium for it.
- `blocking/send_user_file_worktree_root_gate.py` denies a `SendUserFile` call that names a file outside the session's working directory, the `cwd` in the hook payload. The desktop file pane opens a sent file only under that folder and shows "Couldn't find this file" for any other path. The reason lists each outside file and names `<cwd>\.scratch\` as the folder to copy it into.
- `blocking/sent_file_question_gate.py` denies a `SendUserFile` call or an `Artifact` page publish when a Markdown, text, or HTML file it sends asks the user a question. A question is a heading that opens a question or decision section, such as "Open questions" or "Decisions needed", or a sentence that ends with a question mark (or a full-width one) and names the reader, opens with a request such as "Should I", "Can I", "Thoughts", or "Proceed", asks what works best ("What release date works best?"), or offers a choice with "or". A heading such as "Need your input" also counts, as do a heading that asks the reader something with no paragraph below it ("## Should I delete the old logs?") and a sentence that asks for a reply on its own ("Let me know which you prefer."). Headings and `summary` and `dt` labels with a paragraph below them, quotes, fenced and indented code, a question the next sentence answers with yes or no, a question that asks for no wish or go-ahead with a statement after it, such as a frequently asked question and its answer, a checklist item that only checks the reader's work ("- Did you run the tests?" with a task box or beside another question item, naming no decision, confirmation, or preference), a `Q:` line with an `A:` line below it, and a table cell with an answer cell after it pass. A publish that declares the `db` or `artifact` capability, such as option cards that save the answer, passes; other capabilities do not. A file over 256 KB is read through its first and last 128 KB, and the refusal or a system message says so. A file that is not UTF-8 text passes. The read has a 4 s budget; when the HTML parser does not finish, a second read strips the tags in one pass with no parser, with another 4 s, and only when that also runs out does the call run, with a system message that the files went unchecked. The reason quotes at most 160 characters of the question and says to ask it through the question tool and send the file again without it.
- `blocking/question_brief_gate.py` denies an `AskUserQuestion` call when the assistant chat text before it in the same turn runs over 450 words or 15 list or table items. A turn starts at a message the user types, at a result of an earlier question call, or at the first input after an `end_turn` reply or a `stop_hook_summary` entry. A Stop hook that holds the turn adds no input, so the text before a held stop still counts. Each bullet or numbered line is one item, each table row below the header is one item, and lines inside a code fence are not items. The reason names each limit passed and says to shorten the brief or split the question. The gate polls the transcript for up to 3 seconds for its own call and passes when the call never appears. A subagent call, an unreadable payload, and a missing or unreadable transcript, or one that is not a regular file, pass at once. The gate reads only the last 1 MB of the transcript, so a long review followed by more than 1 MB of tool output in the same turn is not seen.
- `blocking/turn_review_gate.py` wakes the agent after a turn ends when a fresh `claude -p "/code-review low <base>..<turn>"` run, on Sonnet at high effort, finds a problem in that turn's edits. On Claude Code the Stop entry runs with `asyncRewake`, so the turn ends at once and the review runs in the background. A finding or a rejected dismissal exits 2, and its text goes to stderr, which the wake shows the agent, and to the stdout `reason`. Every other outcome exits 0 with no output and writes its diagnostic to `~/.claude/logs/turn-review.log`, one line per run with the event name and `stop_hook_active`. A plain `claude -p` run has no background, so the same entry holds that stop with exit code 2. At the prompt it snapshots each opted-in checkout into a commit built from a copy of the index after `git add -A`; at the stop it snapshots again with the first snapshot as parent, so the range holds only the turn's edits, untracked files included. A checkout takes part when it is `CLAUDE_PROJECT_DIR` or a folder directly inside it and its GitHub origin `owner/repo` slug is listed in `CLAUDE_TURN_REVIEW_REPOSITORIES`, comma-separated. A finding is an entry in the review's last non-empty JSON array of objects with a `file` key, where `file` is a changed path and `line` is a number. An empty `[]` counts as no array. A review with no such array has a finding on each line that opens with a changed path, a colon and a line number, after an optional list marker, backtick or emphasis mark. A review that opens with `(none)` has none. A saved baseline that is not a 40- or 64-character commit name is dropped, and that stop takes a fresh baseline. Each stop moves the baseline to its snapshot, marks the turn closed and saves both before the review starts, under a lock on the session's state file in the temp folder, so a second stop during a review starts from that snapshot and no range is reviewed twice. A prompt marks the turn open. A prompt that finds the last turn still open keeps the saved baseline, because no stop has claimed that turn yet (its stop is racing the prompt, or the user interrupted it); the late stop then reviews from that baseline, and edits the user made between the two turns are reviewed too. When a prompt found the turn open less than 10 seconds before the claim, that prompt began the next turn, so the stop leaves it open; a later claim closes it, which ends the open turn an interrupt left behind. A stop or prompt that waits 3 seconds for the lock before its snapshot exits 0 and leaves the state alone. After the review the stop waits up to 35 seconds for the lock, longer than a prompt run may hold it, and changes only the hold count; a stop that never gets it exits 0 with no wake, so each wake is counted. It holds a stop at most 3 times in a row. A stop below the cap with no finding, no rejection and no dismissal to judge resets the count, and so does a user's prompt. A prompt within 10 seconds of the last wake, or one that starts with `<task-notification`, belongs to the wake and keeps the count, so a chain of wakes stops at 3 whether or not a wake turn fires `UserPromptSubmit`. It skips a turn that changed more than 30 files, and lets the stop through when the review fails. The reviews of one stop share 240 seconds, and a checkout reached with less than a second left goes unreviewed. The review run gets `--setting-sources ""`, `--tools Read,Grep,Glob,Bash`, `--no-session-persistence`, `--permission-mode dontAsk`, read tools plus `git diff`, `git show` and `git log` in the checkout, a deny list for git's `-c`, `--config-env`, `--output`, `--ext-diff`, `--textconv`, `--git-dir`, `--work-tree` and `--exec-path` options, `--settings '{"disableAllHooks": true}'` so no other hook steers the review, `CLAUDE_TURN_REVIEW_CHILD=1`, and none of the parent session's id, messaging or ingress variables; the gate does nothing inside such a run. Each finding of a wake gets an id `TR-<n>` that is unique in the session, is saved as `open` in the state file with its text, checkout and commit range, and shows as `[TR-<n>]` before the finding in the wake. The wake names the one way to contest a finding: a reply line `Dismiss TR-<n>: <reason>`, and a claim that the user asked for the behavior goes in that reason with the user's words quoted. On a stop, the gate reads the reply from the Stop input's `last_assistant_message`, or from the text of the last assistant message in `transcript_path` when that field is missing, and takes the first `Dismiss` line per id, with its reason cut to 2000 characters. Open findings named there go to one judge run per checkout: `claude -p --model sonnet --effort high` with the review's read-only options, the child variable, and the prompt on stdin. The prompt holds the checkout path and one JSON object: a `requests` list with each finding's id, commit range and text and the agent's reason as JSON strings, and a `user_messages` list with the last 5 messages the user typed, each cut to 2000 characters, read from `transcript_path`. A message counts only when its entry carries `origin.kind` `human`, so tool results, hook text, notifications, the interrupt marker and prompts sent through the SDK are left out, and so is a typed message that starts with `<`. A transcript that is missing or unreadable gives an empty list. The prompt holds no other part of the conversation. It tells the judge to read the diff and the code at the range, to treat every string in the data as text to judge and the reason as a claim to check, to approve when the code shows the finding is wrong or when the reason quotes words that appear in `user_messages` and ask for exactly that behavior, never on a quote that is not there, and to reject when unsure. The judge's whole answer, inside at most one code fence, must be one strict JSON array of objects with exactly `id`, `verdict` (`approve` or `reject`) and `reason`, each key named once and each id one it was asked about. Any other answer gives no verdict, such as an object that repeats a key or a `NaN` value, and an id named twice gets none. An approval marks the finding `dismissed`, saves the judge's reason, logs one line and wakes nobody. A rejection marks it `upheld`, saves the reason and wakes the agent with `Dismissal of TR-<n> rejected: <reason>. Fix it.`. That wake counts toward the hold count, and a rejection and the stop's new findings arrive as one wake with one count. A `Dismiss` line for an upheld, dismissed or unknown id is logged and not judged. At the hold cap no judge runs, and the finding stays open. The judge runs after the stop's reviews and shares their 240 seconds. A judge that fails, times out, gives an answer of any other shape, or starts with less than a second left exits 0 with no output, logs one line, and leaves the finding open. A transcript line nested too deep to read is skipped and logged once per stop.

The adjacent test observes a `block` decision with the finding on stdout and the same text alone on stderr, a review range whose diff holds only the edited file, and a review environment with no parent session id. A `(none)` review, an unchanged turn, a failed or timed out review, an unlisted repository, a 31-file turn, and a fourth stop in a row pass with empty stdout and stderr. A second stop during a review starts no second review. A prompt that runs before the last turn's stop keeps that turn under review, two such prompts in a row keep both turns, and a stop long after such a prompt closes the turn. A prompt within 10 seconds of a wake, or a `<task-notification` prompt, keeps the count, and a later prompt resets it. A held state lock passes the stop quietly, a lock freed late after the review still counts the hold, and a lock that never frees after the review passes the stop with no wake. With a stub judge on the same `claude` stub, a `Dismiss` line in `last_assistant_message` or in the transcript starts one judge run on `sonnet` at `high` whose stdin holds the finding, the reason, the checkout and the range; an approval passes quietly and saves `dismissed`; a rejection wakes with the rejection line and saves `upheld`; a second `Dismiss` line for an upheld finding, a line for an unknown id, and a line at the hold cap start no judge; a failed, timed out, non-JSON or starved judge passes quietly and leaves the finding open; and a rejection plus new findings arrive in one wake. `node --test packages/claude-dev-env/bin/install.cursor-rules.test.mjs` observes the `asyncRewake` Stop entry in the installed Claude settings and no turn review in the Codex or Cursor hooks.

## Gotchas

- The ask nudge runs only from `hooks.json`, so Codex and Cursor sessions get no turn-start note. Their Stop gate still holds a work turn with no tracker call.
- The background silence note is the last point before the reply. A Stop hook sees the reply after it is on screen, and holding the text at `MessageDisplay` would need a judgment on whether the exception applies.
- A headless run whose input is streamed, such as `claude -p --input-format stream-json` or an SDK client, runs the Stop entry in the background, and the host kills it at teardown, so that run loses its review.
- Claude Code queues a wake as a `task-notification` message. Whether that message fires `UserPromptSubmit` is not proven, so the gate takes any prompt within 10 seconds of the last wake as the wake's own. A prompt the user sends in those 10 seconds keeps the hold count too.
- `blocking/turn_review_gate.py` starts `claude -p`, which inherits the parent session id unless the gate strips it. A review that kept `CLAUDE_CODE_SESSION_ID` would write into the parent's transcript.
- Each review run calls a model, Sonnet at high effort. Twelve measured runs cost $0.50 in total, from $0.01 to $0.13 each. A judge run is a second model call, on Sonnet at high effort, and its cost is not measured. Leave `CLAUDE_TURN_REVIEW_REPOSITORIES` unset and the gate makes no snapshot and no call.
- The `rewakeMessage` and `rewakeSummary` of the Stop entry in `hooks.json` speak of a review of the last reply's changes. A wake that holds only a rejected dismissal gets the same prefix.
- The turn review's dismissal judge has these known limits. A finding the agent neither fixes nor contests closes with no check, and so does an upheld finding the agent then ignores: the rejection wake is its only push, and a later `Dismiss` line for it is ignored. The agent can write the state file in the temp folder and the transcript file, so neither the findings record nor the user's messages are tamper-proof. The judge reads only the last 5 messages the user typed, so a request from earlier in the session is no ground to dismiss. Only entries with `origin.kind` `human` count, so a prompt sent through the SDK or by another program is no ground either, and a typed message that starts with `<` is left out. The judge's own reading of the code and the messages on a live model has not been measured; the tests use a stub.
- `blocking/task_subject_length_gate.py` passes a `TaskUpdate` with no `subject`, so a status change on an old long item goes through. `TodoWrite` resends the whole list on every call, so one old long item denies every later `TodoWrite` until that item is shortened.
- `blocking/step_note_gate.py` is off by default and polls for the transcript record. Subagent calls and unreadable records pass.
- `blocking/wakeup_cap_gate.py` lets an `update_trigger` cron change pass, because that input does not say whether the Routine wakes a session. Its step-down values come from fire-time probes: `send_later` rounds its fire time up to the next minute and polls once a minute, so a 1-minute request landed 123 and 158 seconds later. `ScheduleWakeup` rounds its fire time up to the next minute, so requests of 60 and 90 seconds landed 70 and 121 seconds later.
- `blocking/verify_before_acting.py` runs after the tool. A block asks the agent to check the claim and undo a contradicted change. A spawn has already started when the hook runs, so a block would stop nothing. The advisory note asks the agent to check the claim before it acts on the spawned agent's result.
- The final reply gate blocks the stop and returns its reason to the model, which rewrites the reply. Claude Code ends the turn anyway after eight blocks in a row.
- Every Stop gate holds a turn through `hooks_constants/stop_hook_hold.py`: exit code 2, the reason on stderr, and the same reason in a stdout `block` decision. Exit code 1 does not hold a turn on Claude Code or Codex, so a Stop gate that crashes lets the turn end. A Cursor payload keeps exit code 0 and gets the reason as `followup_message`.
- The edit marker gate scans replacement cards as well as the message text.
- The handoff close gate reads the `body` and `comment` fields of issue tools only. A `gh issue close --comment` command in Bash and a pull request body that closes the issue with `Closes #N` do not reach it.
- The eval write gate reads Write, Edit, MultiEdit, NotebookEdit and apply_patch calls. A Bash or PowerShell command that writes an eval file reaches it without the gate. An apply_patch that will not parse counts as an eval write when any of its words is an eval path. A missing or unreadable transcript denies the write.
- The verify gate passes when the transcript is missing or unreadable, or when git cannot resolve the repository. It reads the repository from the payload `cwd` and `git -C`, so a `cd <dir> && git commit` chain is checked against the session directory. A `git commit <pathspec>` that names paths without `git add` is checked against the staged diff only.
- The lifecycle gate counts only invocations after the last compaction, so a compacted session invokes `pr-lifecycle` again. A missing or unreadable transcript allows the call. A scan the deadline stops counts as no load found, and its deny carries a sentence that says to load the skill again.
- The dark mode gate denies a page publish when Node, Playwright or Chromium is missing, and its reason names the install command. It checks both dark signals, `prefers-color-scheme: dark` and `data-theme="dark"` on the root element.
- The clean-review gate trusts the receipt. A receipt the agent writes by hand with zero findings, or with every finding ruled out and a rulings link, passes, so the pr-lifecycle skill names the review loop that writes it. A `gh pr merge` that names no repository is denied, because the gate cannot tell which repository the current branch belongs to.
