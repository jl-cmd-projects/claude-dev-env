# Proof before a pull request

## In brief

A live proof is for behavior a test process cannot reproduce. The paths a pull request changes set its evidence tier, and the tier sets the proof the body owes:

| Tier | When | Proof in practice |
|---|---|---|
| none | Every changed path is a doc or a test, and none is a live surface | Optional. CI is the evidence. |
| checked | Code changed, and no changed path is a live surface | A command you ran to check the change. A test run counts. |
| live | A changed path is a live surface, the gate cannot read the list, or the command runs more than the pull request call | A run of the changed thing where it runs, with and without the change. |

Proof first, then the PR. This binds every agent, script, CI job, and automation. Unproven: leave it unopened and tell the user.

**When this applies:** Every session that builds a change and opens a pull request, in every project.

## Rule

Before you open a pull request, find its tier, then give the proof that tier asks for.

A live surface is a path whose behavior depends on something a test process cannot reproduce:
- An agent surface: a `SKILL.md`, `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `copilot-instructions.md`, `hooks.json`, `.mcp.json` or `settings*.json` file, or a file under a `skills`, `rules`, `agents`, `commands`, `system-prompts` or `output-styles` folder. Names match in any case, so `Skills/x/skill.md` counts.
- Any file under a `.github/` folder, such as a workflow, an action, `CODEOWNERS` or `dependabot.yml`.
- A page people see: `.html`, `.htm`, `.css`, `.scss`, `.tsx`, `.jsx`, `.vue` or `.svelte`.
- The `.claude/live-surfaces.txt` file itself, and each path a glob in the base branch's copy of that file names, except a test file. A test under a built-in live surface, such as `skills/`, stays live.

A repository names its other live surfaces in `.claude/live-surfaces.txt` at its root: one glob per line, with `#` comment lines and blank lines skipped. A `#` after a space or a tab starts a comment to the end of the line, so `portal/  # seller portal` declares `portal/`. A line that ends in `/` covers every path under that folder. A line with no `*`, `?` or `[` names that exact path, or every path under it when it is a folder. Any other line matches the whole path, and `*` crosses folders. The file is read as UTF-8, and a leading byte order mark is dropped. A file whose bytes do not decode as UTF-8 declares nothing, so code stays live. The gate reads the base branch's copy, so a pull request cannot lower its own tier. A repository with no such file keeps every path that is not a doc or a test on the live tier.

A doc or a test is a file with a docs ending (`.md`, `.txt`, `.rst`, an image), a data file under a `docs` folder, a file under a `tests`, `test` or `__tests__` folder, or a test file name (`test_*`, `*_test.py`, `.test.`, `.spec.`, `conftest.py`). A `requirements*.txt` or `constraints*.txt` file is code, in any case.

Run the `gh pr create` or `gh pr edit` call alone, as a command of its own. The gate reads the changed paths before the command runs, so a `cd`, a commit, a checkout or any other command joined to the call by `&&`, `;`, `||`, a pipe, a new line, a subshell or a wrapper such as `bash -c` gives the live tier. Commit and push first, then run the call by itself from a checkout of the head branch, or name the repository and head branch with `--repo` and `--head`. A `--base <branch>` on the create is honored: the gate reads the changed paths and `.claude/live-surfaces.txt` against `origin/<branch>`, then `<branch>`. With `--head <branch>`, push the branch first: when `origin/<branch>` names another commit than the local branch, the gate cannot trust the local list.

For the checked tier, list each command you ran in backticks under "Proof in practice" and quote the output that shows the result. A test run is enough.

For the live tier, what counts as proof:
- You ran the changed thing the way its user runs it, and you saw the effect it exists to produce. A hook fires in a live Claude Code session and changes what that session does. A script runs from its launcher on inputs like the ones it will meet. A skill or rule changes what a fresh agent does with an ordinary request.
- You saw the failure first. Run the same scenario without your change and record what goes wrong. The proof is the difference between the two runs.
- You covered the conditions the change will meet. That includes the case it should leave alone, and for session behavior a fresh session, a resumed session, a later turn, and a session after compaction.
- The session under test got an ordinary request, worded as a task the way the owner would ask for it.

In the live tier, unit tests are welcome as extra evidence. The live run is the proof. A test you edited until it passed proves nothing.

For a change to Claude Code behavior, such as a hook, skill, rule, setting, prompt or output style:
- Spawn every session through the account broker, with the stream saved to a file:
  python ~/.claude/scripts/account_broker.py run --product claude --report <broker-report.json> -- claude -p "<request>" --model claude-opus-5-5 --effort medium --output-format stream-json --verbose > <stream.jsonl>
- Run each later turn the same way with `--resume <session id>`. The broker resumes a session on the account that started it when that account has room.
- Keep `--model` and `--effort` on every call, with a pair from [Subagent model and effort](subagent-model-effort.md). Without them the headless run uses claude-sonnet-5-5. Confirm the served model in the result's `modelUsage`.
- Start the broker from your own shell, with your environment as is. The broker reads the account meters with your session's credentials and starts Claude without your session's variables.
- In a cloud session, where `CLAUDE_CODE_REMOTE` is `true`, the broker reads no meter and runs the job on the session's own account. The report's reason starts "cloud session:".
- Leave out `--bare` and `claude plugin eval`. Both drop the hooks and settings the user runs with.
- Read the broker report for the account it chose. Read the stream for the hook events and their output, `permission_denials`, the final result, and the token usage on the result event.
- When the broker exits 3 with action "wait", read its reason. Start headless Claude only through the broker.
  - "no account has room" means each account is below its usage floor. Treat that as a blocked proof and report the reason and `resets_at`.
  - "no readable account has room" means each read account is below its usage floor, and the reason names the accounts whose meter went unread. Run the broker once more after `resets_at`. When it waits again, treat that as a blocked proof.
  - "no account meter could be read" means the meter reads failed, often with HTTP 429. Usage may be left, and `resets_at` is when the broker checks again. Run the broker once more after `resets_at`. When it waits again, treat that as a blocked proof.
  - A cloud session never gets the two unread-meter waits, because the broker reads no meter there. A wait in a cloud session means the session's own account hit its usage limit on a broker run. Treat that as a blocked proof and report the reason and `resets_at`.

Report it in the pull request body under "Proof in practice". List each command you ran, quote the output lines that show the effect, and state the difference between the runs with and without the change. The run on the target the change exists to fix belongs in this section before the pull request opens. List a condition the change does not target, such as an older data shape, under a "Not covered" heading at the same level.

A workflow file the pull request adds cannot run until it reaches the default branch. For that run only, add an "After merge" heading to the body. Under it, name the added workflow file in backticks and say who records the first run's link. Prove everything else the workflow does before the pull request opens, such as its script and tests.

When you cannot prove it, leave the pull request unopened. Tell the owner in three short sentences what you could not run and which tool would make it possible. A blocked proof is an acceptable result, because it shows where tooling is missing.

## Enforcement

`hooks/blocking/pull_request_proof.py` reads the body of each new pull request before it opens. `pr_lifecycle_skill_gate.py` runs it on each create spelling `hooks/blocking/followup_pr_dedupe.py` reads, and on each `mcp__*__create_pull_request` tool. The spellings are `gh pr create`, `gh pr new`, `gh` with a root `-R` or `--repo` before `pr`, a `GH_REPO=` prefix, and the `pull_request.py create` script run by any `python`, `python3.x`, `py` or `uv run` launcher, with interpreter options or a path to the script. A shell command that runs anything besides the one create call gets the live tier with no read, and its deny says to run the call alone. The gate first reads the paths the create changes: from git in the session directory when that checkout's `origin` is the repository the create names, else from the GitHub compare API. A git read takes its merge base with `origin/<base>` when the create names `--base`, else with `origin/HEAD`, `origin/main` or `main`. A named base with no `origin/<base>` in the clone falls to the compare API, since a local branch of that name can differ from the copy GitHub compares against. With `--head`, a local branch whose commit differs from `origin/<head>` gives no git answer. A rename adds both of its paths. The declared globs come from `.claude/live-surfaces.txt` at the merge base for a git read, or on the base branch through the contents API for a compare read. A list git and the compare API cannot read, an empty list, or a compare answer at its 300-file cap gives the live tier. A body whose proof section passes the live rules triggers none of these reads. In the none tier, a body with no "Proof in practice" heading passes. In every tier, the gate denies a section that is there when the text under the heading names no command in backticks, and in the live and checked tiers it denies a body with no such heading. In the live tier only, the gate also denies a section whose only commands run a test runner, such as `pytest`, `python -m unittest`, `uv run pytest`, `npm test`, `npx vitest`, `jest`, `go test` or `cargo test`. Quotes around a runner word, interpreter flags before `-m`, and `coverage run -m unittest` are still test runs. A command is an inline backticked span or a `$ ` line inside a fenced block. A span that starts with a path and line, such as `gate.py:12`, is not a command. A span that holds one path or file name, such as `src/x.py`, is not a command unless that span runs a test runner, such as `py.test` or `pytest.exe`. A test run piped into `tee`, `tail`, `head`, `grep` or `cat` is still a test run. The deny quotes the line "Unit tests are welcome as extra evidence. The live run is the proof." and asks for a run of the changed thing the way its user runs it, without the change and with it. Each of these denies ends with the tier and the reason for it: the first live-surface path, the first code path when the base has no `.claude/live-surfaces.txt`, the unread file list, or a command that runs more than the pull request call. In every tier, the gate also denies a section whose prose says part of the change is not proven, not tested or not verified, with "yet", "been" or "fully" allowed after the "not", or says unproven, untested or unverified. The line passes only for a workflow file the branch adds, when the body's "After merge" heading plans that file's first run; `pull_request_proof.py` and `hooks_constants/pull_request_proof_constants.py` hold the exact conditions. Otherwise the deny quotes that line, and asks for the run before the pull request opens, or for the line under a "Not covered" heading when the change does not target it. The same denial covers a proof line that opens with "not run", "not exercised" or "not executed" (a "yet" or "been" may follow the "not") or says "has not been run". A proof line with a merge word (merge, merged, merges or merging, so post-merge too) is denied with its own reason: run the check on the branch, and put a file or command name that contains merge in backticks. A step that needs the merged code to exist goes under a "Not covered" heading at the same level as the proof heading, as a line that opens with "not run". `UNPROVEN_ADMISSION_PATTERN` and `MERGE_WORD_PATTERN` list the shapes. Words inside backticks or a fenced block are quoted output and do not count. A section with one command that is not a test run, and no such line, passes. A `gh pr create` with no `--body` or `--body-file` is denied with a request for the body. A body edit through `update_pull_request`, `gh pr edit` or the `pull_request.py edit` script gets the same checks on its proof section that a new pull request of its tier gets, so an edit cannot swap in a proof that a new pull request of that tier would be denied. A `gh pr edit` or `pull_request.py edit` takes its tier from the session checkout, the same with or without a pull request number, when the checkout's `origin` is the repository the edit names and git can list the changed paths. An edit through `update_pull_request`, or one whose changed paths git cannot list, gets the live tier. An edit with no proof section passes. The gate also denies a new pull request whose "What this does" section holds no flowchart: a closed `mermaid` block whose first line starts with `flowchart` and that joins two nodes with an arrow. A body edit meets the same check when its body carries a "What this does" heading. A body the gate cannot read passes, such as an inline multi-line `--body`, a body from standard input, or a body written through `gh api`. A `--body-file` that is not a regular file (a pipe, a device or a directory) counts as no body: a create is denied with the request for the body, and an edit passes. Merges and pushes pass.

The gate also measures each new pull request against its own base, which is the `--base` branch the create names, else the branch `branch.<name>.gh-merge-base` names in git config, else the repository's default branch. `hooks/blocking/oversized_change.py` counts the lines added and deleted since the head left that base, with git in the session directory, or with the GitHub compare API when git cannot tell. A file `.gitattributes` marks `linguist-generated` and a lockfile such as `uv.lock` or `package-lock.json` count zero, and so does a binary file. The compare API leaves out only lockfiles. A stacked level created with `--base <parent-branch>` counts only its own lines. Over 1,000 lines, the gate denies the create and points to `~/.claude/skills/pr-lifecycle/reference/split-a-pull-request.md`. A body with a "Why one pull request" heading, at any level, with the reason under it, passes up to 2,000 lines. Over 2,000 lines the gate denies the create whatever the body says. When git cannot read the named base and the compare API gives no answer, the gate counts against the default branch; that count can hold the levels below, so it is held to the 1,000-line bar only. When the compare API returns its 300-file cap, its count is a lower bound: over 1,000 listed lines the gate denies a body with a reason too, and asks for the base branch to be fetched so git can count the whole change. When git and the compare API cannot read the size, when the compare API returns its 300-file cap and lists 1,000 lines or fewer, or when no base resolves, the create passes. A body edit is not measured.

When the checked-out branch changes a file people see (`.html`, `.htm`, `.css`, `.scss`, `.tsx`, `.jsx`, `.vue`, `.svelte`), the gate also denies a body whose proof section holds no picture: a markdown image, an image URL, or an Artifact page link that shows the screenshots. Render the change, read the screenshot, and put it in the section, so the reader sees what you looked at. A page the branch only moves to another folder or name that ends the same way, with every byte kept (`R100` in `git diff --name-status`), changes nothing people see, so the gate leaves it out; a moved page that also changed, or a file that becomes a page by a change of name ending, still needs the picture. When git in the session directory cannot list the branch's changed files, the gate asks for the picture as well. The gate looks for the picture first, so a proof section that holds one passes this check with no git read.

The gate's git, GitHub CLI and web reads share one budget, counted from the gate start: the proof and picture reads have a deadline at 12 s, and the follow-up reads at 20 s. A stopped child read gets 1 s more to close its pipes, and a scan finishes the line it is parsing before it stops. The registered timeout in `hooks.json` is 30 s, and the budget test in `test_gate_run_reads.py` reserves two such graces and a 5 s margin inside it. A read the budget cuts short comes back unanswered, and the check that asked for it decides from that. A deny from such a run ends with a sentence that says the reads ran out of time, so a second run may pass. The `pr-lifecycle` transcript scan answers to the 12 s deadline. A scan reads the clock before each file block and before each line, and a line over 16 MiB ends the scan as a passed deadline does. A scan the deadline stops counts as not found, and its deny says to load the skill again. A transcript that cannot seek to its end is first copied forward into memory, and a copy that passes 64 MiB ends the scan as a passed deadline does. On POSIX a stopped child read is killed with its process group, and a process that left that group by starting its own session is outside it. On Windows the child joins a job object right after it starts, and the gate ends the job, which also ends a grandchild that still holds the pipe after the child exited. When no job could be made or ended, a bounded `taskkill /T /F` runs instead. A process the child starts before it joins the job is outside the job. A follow-up create is refused when the read of the open pull request list gets no answer in time, or when the create names no repository and the origin remote cannot be read.

The gate checks that the section its tier asks for is there, names a command, and admits no unproven part. Whether the run proves the change stays a judgment for the author and the reviewer. `hooks/blocking/evidence_tier.py` holds the tier rules and the docs-or-test classifier the verify-before-commit gate also uses.
